# Translations and themes

## Languages

The popup, side panel, options page and web page read their text from
dictionaries in `src/shared/i18n/locales/`:

- `en.ts` is the source: every message key is defined there.
- `hu.ts` (and any further language) is typed against it, so a missing or
  misspelled key fails `svelte-check` / `tsc`, and
  `tests/shared/i18n.test.ts` checks that each translation keeps the English
  message's `{placeholders}`.

In a Svelte component, import the reactive helpers; text re-renders when the
language changes:

```svelte
<script lang="ts">
  import { t, tp } from '../../shared/i18n/reactive';
</script>

<h2>{t('history.title')}</h2>
<span>{tp('common.spans', count)}</span>
```

Plain TypeScript (models, shared modules, tests) uses `translate` /
`translatePlural` from `src/shared/i18n`. Plurals are keys with `_one` /
`_other` suffixes, chosen with `Intl.PluralRules`.

### Machine-translated languages

Every other language Google Translate offers (about 130) is machine-translated
by [KO_language_translator](https://github.com/HunKonTech/KO_language_translator),
included as the git submodule `KO_language_translator/` (tracking its `main`
branch). Do not edit its output by hand:

- `src/shared/i18n/generated/locales/<code>.json` — one dictionary per
  language, keys a subset of `en.ts` (missing keys fall back to English). A
  language nothing has been translated into yet has an empty `{}` file.
- `src/shared/i18n/generated/index.ts` — `GENERATED_LOCALES` and each
  language's own name; `index.ts` adds them to `SUPPORTED_LOCALES`. Every
  language the translator offers is listed, so the language picker shows it
  even while its translation is incomplete (untranslated text is English).
- `src/shared/i18n/generated/source.json` — the English text the translations
  were made from.

The builds copy the JSON files to `i18n/` (extension, IDE panel, web page) and
`setLocale` fetches a language's file the first time it is used (`loadLocale`),
so only English and Hungarian are in the bundles. The web page's service
worker caches a dictionary when it is first loaded rather than on install.

`scripts/i18n/machine-translate.js` (`npm run i18n:translate`) drives the
translator: it lists the languages Google offers that the translator can
handle (`scripts/i18n/list-languages.py`), writes the
`const DICTS = { en, <lang>, … }` file `main.py --new-only` expects for a batch
of languages, and reads the result back into the JSON files. It only
translates keys a language lacks, and translates a key again when its English
text changed (compared with `source.json`). Translations that lose a
`{placeholder}` are dropped. Each batch is saved when done; after
`--time-budget` minutes (or when Google stops answering) the run ends and the
rest follows next time. Other options: `--only de,fr`, `--batch <n>`,
`--force` (everything again), `--python <exe>`, `--translator <dir>`.

To run it locally:

```bash
git submodule update --init --remote KO_language_translator
pip install deep-translator
npm run i18n:translate -- --only de --time-budget 10
```

### The I18N workflow

`.github/workflows/i18n.yml` runs on every push to `main` (and by hand, with
`force` and `time_budget_minutes`, default 60). It updates the submodule to the
translator's latest `main`, runs the script and commits changed dictionaries to
`main` with `GITHUB_TOKEN` (which starts no new run). **Build and Release**
starts when I18N completes (`workflow_run`) and builds the latest `main`, so
every release carries the current translations; tags and manual runs still
start it directly. Rate limits or failed requests never fail I18N: the
affected keys stay in English until a later run. The translator sends many
texts of a language in one request (`--batch-chars`, 3000 characters by
default), so a complete translation of every language is roughly a thousand
requests rather than one per key and language.

When Google blocks the self-hosted runner's IP (the run warns that Google
refuses requests and skips translating), start **I18N (GitHub-hosted)**
(`.github/workflows/i18n-hosted.yml`) by hand: the same job with the same
inputs on a GitHub-hosted runner, whose IP differs on every run. It also
commits to `main` and starts Build and Release when it finishes.

### Adding a hand-written language

1. Copy `hu.ts` to `<code>.ts` and translate the values.
2. Add the code to `SUPPORTED_LOCALES` and `LOCALE_NAMES`, and the dictionary
   to `dictionaries`, in `src/shared/i18n/index.ts`; add it to
   `MANUAL_LOCALES` in `scripts/i18n/machine-translate.js` so the translator
   leaves it alone, and delete its generated JSON.
3. Run `npm test` and `npm run check:svelte`.

`registerMessages(locale, messages)` adds or overrides messages at runtime.
Keys a dictionary lacks fall back to English.

Not translated yet: the review overlay and other in-page UI on chat sites,
the toolbar badge texts, and status text produced by shared modules (system
check notes, resource summaries).

## Theme and language preference

`src/shared/ui-prefs.ts` keeps `{ theme: 'system' | 'light' | 'dark', locale:
'auto' | Locale }` in `chrome.storage.local` (`pg_ui_prefs`), mirrored
to `localStorage` so a page paints in the right theme before the async read.
Each entry point calls `initUiPrefs()` before mounting.

The theme is set as `data-theme` on `<html>`. `src/shared/styles/tokens.css`
defines the light tokens and redefines them for `[data-theme="dark"]` and,
for `system`, under `prefers-color-scheme: dark`. Components use the tokens
(`--color-card`, `--color-input`, `--color-on-accent`, `--tone-*`, …) instead
of literal colors. IDE webviews set `data-ide-host` and map the tokens to the
IDE's colors instead (`src/ide/theme/ide-base.css`).
